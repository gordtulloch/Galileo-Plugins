# Changelog

## [Unreleased]

### Changed

- **Ported to core's own replication and Connect Link (2026-11-02).** The plugin had been written against a local replication API that was discarded when origin's complete core was merged; it now sits on `galileo.replication` as shipped (registry with `key_of`/`wire`/`replicates`, `apply_mode`, `RevisionIssuer`, `SyncStore`) and Connect Link's route signature `handler(peer, request)`. Differences that matter: a wire row is now the flat row (a parent named by its natural key, e.g. `pier: [observatory, pier]`) instead of `{key, fields}`; a table's natural key on the wire is `[wire[c] for c in natural_key]`; deletions have no revision of their own, so each table carries a **tombstone cursor** (`"<table>#t"`, the tombstone id) beside its revision, in pulls, in `last_rev` and in acknowledgements, and tombstones are released by id once every paired node has acknowledged them; a deletion the Master applies for a spoke is recorded as a tombstone so other spokes learn of it; a deletion of a row is treated as a change after that row's last revision, so an edit based on that revision conflicts and the later edit wins (it previously did not, because the deletion had no revision); deletion records of node-local rows (core records those too) are never sent. New `nodeconnect.repl` (find a local row by wire key, record/drop a tombstone) and `nodeconnect.store.NodeStore` (key lists and whole snapshot records over core's `SyncStore`). All 40 tests pass against the merged core, including the real-listener ones; the revoked-node lockout now rides on core's own peer handling.

### Added

- **Plugin shell (`plugin.toml`, `nodeconnect.plugin`, `nodeconnect.runtime`); the plugin now builds and loads.** `NodeConnectPlugin` (settings namespace `plugin.NodeConnect`) builds a `Runtime` from core's services and starts it; a failing start leaves the plugin inert rather than raising, and enabling or disabling it starts or stops the runtime (`NCON-010`, `-530`, `PLUG-060`). A node with a Master designated is a **spoke**: if paired it runs one background `SyncWorker` (a pass at once, then every `sync_interval_s`, default 300 s, or after the jittered back-off when a pass fails, or immediately on `sync_now`) and asks for no listener; if designated but not yet paired it starts nothing. Any other node is a **Master**, or standalone and able to be asked to be one: it takes a place on Connect Link with exactly the four node permissions and installs the `/nodeconnect/v1` routes, re-installed after every listener restart. Stopping joins the thread and releases the place, so a disabled plugin leaves no thread and no routes (`NCON-310`). `plugin.toml` is checked against core's own manifest reader. Eight tests in `tests/test_ncon_shell.py`. Needs the core change that lets a plugin's routes survive a listener restart (`ConnectLinkService.acquire(..., install)`). `build_plugins.py nodeconnect` builds the ZIP; the `plugins.json` marketplace entry is deliberately not committed until a release exists. Not yet built: UI and Options page (so pairing cannot yet be started from the app), snapshot/report retention, transfer and history, OpenAPI, help, wiki.

- **Logic modules, tested against core's replication facilities** (no plugin shell yet, so still no `plugin.toml` and not packaged). `roles` derives spoke/Master/standalone from facts and refuses a node being both (`NCON-020`). `codec` filters what may leave the node (node-local items and secrets stay home unless the user opts in), pages rows at 200 without building a table in memory, and merges a received row field by field so a node-local value on the receiver is never overwritten (`NCON-100`, `-110`, `-210`). `conflict` measures the clock offset from a round trip, decides a pushed change exactly by base revision (the later offset-corrected edit wins, a tie goes to the Master, the loser is named for the snapshot) and works out how far tombstones may be released (`NCON-160`, `-170`, `-180`). `compat` turns the handshake into full, partial or refused with a message naming what to upgrade (`NCON-305`). Nine tests in `tests/test_ncon.py` (`TC-NCON-020`, `-100`, `-110`, `-160`, `-170`, `-180`, `-210`, `-305`).

- **Apply step (`nodeconnect.apply`).** Received changes are staged in core's durable inbox before anything is applied, so they can be acknowledged at once (`NCON-200`); `ApplyGate` applies them immediately when the node is idle and by itself when a running session ends, and rows of a table that failed stay staged for the next try. `Applier` writes each table in its own transaction in dependency order (a failing table rolls back alone), upserts parents-first then deletions children-first, writes through the model so its defaults fill any column the sender did not carry, never guesses at unknown columns, leaves a row with an unacknowledged local edit for the Master to arbitrate, defers a row whose parent is missing, applies but reports a loopback device address, and never rewrites a node-local value or receives a secret (`NCON-110`, `-190`, `-210`, `-230`). Every replaced or deleted value, including rows removed by a cascade, is snapshotted first; `restore` writes a run back as ordinary local edits so it replicates, re-resolving foreign keys by name (`NCON-220`). Eight tests in `tests/test_ncon_apply.py`. Known limit: a table's upserts and deletions in one batch are two transactions, not one.

- **Sync engine.** `master.MasterService` (commit local edits, changes since per-table revision, exact arbitration of pushes, acknowledgements, tombstone release) and `sync.SpokeSync` (handshake and compatibility, pull, stage and apply through the gate, push, adopt the Master's answers, acknowledge, back-off) against an abstract `MasterLinkPort`. Nine tests in `tests/test_ncon_sync.py` run two real databases and cover first sync, incremental pull, push, both conflict directions with snapshots, deletions both ways with tombstone release, protocol refusal, partial sync on an older schema, deferral during a session and back-off.

- **Wire and spoke link (`nodeconnect.wire`, `nodeconnect.link`).** The `/nodeconnect/v1` routes `handshake`, `pull`, `push` and `ack` are registered on core's Connect Link route registry, reads under `config.read` and pushing under `config.write`; the node the Master acts on is always the authenticated peer, never a name in the body. A pull is paged (200 per page) and a page that does not finish its table reports its own last revision, so an interrupted pull resumes where it really stopped. A node that is itself a spoke answers every request 409, and a malformed push or an unknown table is a 400. `MasterLink` implements the spoke's port over a transport; the HTTPS transport pins the Master's certificate by the fingerprint shown at pairing and sends nothing, the token included, unless it matches. Four tests in `tests/test_ncon_wire.py` run the full sync with every message serialised to JSON and back. Not yet exercised against a real listener: the HTTPS transport and its pin check are untested, and the pairing client that obtains the token and fingerprint is not built.

- **Pairing (`nodeconnect.pairing`).** Uses core's Connect Link pairing rather than a second mechanism. On the Master, `PairingDesk` lists only NodeConnect's pending requests (code, name, platform, source; never a token), approves with exactly `config.read`, `config.write`, `data.push` and `data.pull` (never `control` or `view`), refuses to approve while the node is itself a spoke, and lists paired nodes with their reported Galileo and database versions (recorded at handshake). Revoking keeps a node (it still holds tombstones back); deleting forgets it and its acknowledgements so it no longer does (`NCON-040`, `-180`). On the spoke, `PairingClient` requests pairing, returns the confirmation code to show, collects the one-time token on approval and stops if the certificate that answers is not the one the Master reports for itself, or changes before collection. Credentials are node-local: address and fingerprint in the `plugin.NodeConnect` settings namespace (which core never replicates), the token in the OS credential store and never in the database (`NCON-060`). Six tests in `tests/test_ncon_pairing.py` use core's real `PeerStore` and `PairingService`. `link.open_transport` (HTTPS for the unauthenticated pairing calls, reporting the presenting certificate's fingerprint) is untested against a real listener.

- **Verified over a real Connect Link listener** (`tests/test_ncon_listener.py`, 3 tests). Core's `LinkServer` runs on a loopback port with its own self-signed certificate; a node pairs through `open_transport`, pinned to the fingerprint the Master reports, then handshake, pull, push and ack all answer through the certificate-pinning `https_transport`, and the Master records the node's version and acknowledgement. A transport pinned to another certificate refuses before sending the token, a bad token gets the bare 401, a revoked node is locked out at once, and an unreachable Master raises `LinkError`. This closes the earlier gap that the HTTPS transports had never met a real server. One database serves both ends in these tests, so they cover the network path, not sync logic (covered between two databases elsewhere).
