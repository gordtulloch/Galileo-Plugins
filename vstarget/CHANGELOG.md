# Changelog — vstarget Galileo plugin

All notable changes to this plugin are documented here ([Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format).

## [Unreleased]

### Added

- **Photometry runs off the UI thread (core `NFR-PERF-020`), with progress and a Stop button.** A run used to happen in the Run Photometry slot itself, one `asyncio.run()` per frame, which froze the whole window for as long as the measuring took — minutes for a few nights of frames, with no indication it was working. `vstarget/analysis/runner.py` splits the run: `build_jobs()` resolves the selected sessions into self-contained jobs (frames, target with coordinates, filter band) and stays on the UI thread where the library and plan-store connections live, while `run_jobs()` measures with no database or Qt involvement. `PhotometryThread` wraps it in a `QThread` with one event loop for the whole batch, built lazily like the planning panel's `FetchTargetsThread` so the module imports without Qt. The panel reports "Measuring frame N of M" as it goes, disables the controls that would change the run under it, and Stop ends the run after the current frame while keeping the measurements already made. A run still going when the panel closes or the app quits is cancelled and waited for, rather than leaving a `QThread` to be destroyed mid-flight.

- **The "Aperture radius (px)" field is now actually used.** It was read from the panel and then dropped on the floor: `VariableStarAnalysis` always built `AperturePhotometryEngine()` with its 8 px default, so changing the field changed nothing. `VariableStarAnalysis` now takes `aperture_radius` (and optional annulus radii) and the panel passes the field through, rejecting a non-positive or unreadable value before any frames are read. An unspecified sky annulus scales with the aperture at the same 1.5x/2.5x proportion the engine's defaults use, because a fixed 12-20 px annulus sits *inside* an aperture the user widens past 12 px — the star would have been measured as its own background.

- **`TC-VST-AN-040`/`TC-VST-AN-100` tests added** for the aperture wiring (default, scaled annulus, explicit annulus override, and the radius reaching the engine through `run_jobs`) and for the runner (`build_jobs` resolving sessions to frames with per-session target/filter, the single-selection name override, the catalogued-filter fallback, sessions whose frames have left the disk, and `run_jobs` progress reporting plus cancellation keeping partial results).

- **The analysis panel's Input Images section is now library-based, not folder-based (`VST-AN-100`).** It used to ask for a directory of FITS files, which meant knowing where the library had filed the frames and then measuring whatever happened to be in that folder. It now lists the image library's own sessions for every target designated a variable star — the `VariableStars` row written by Library > Images > right-click > *Add Variable Star* — grouped by target, each session showing its date, filter, frame count, telescope and exposure, with multi-select (selecting a target takes all of its sessions). The list re-reads the library whenever the panel is shown, and a Refresh button covers a target designated while it is already open. Target star and Filter band fill themselves in from a single-session selection; a wider selection reports each session under its own catalogued target and filter, so one run can cover several nights or several stars. The target's RA/Dec now comes from the saved observation plan when the star is in one, so the photometry aperture lands on the star instead of the centre of the frame. Where no target has been designated yet, the panel says so and names the context-menu action to use.

- **`vstarget/analysis/library_sessions.py` added** — the read side of that: `variable_star_targets()`, `list_variable_star_sessions()`, `session_frames()` and `session_target_coordinates()`, over core `galileo.library`'s own models rather than a database of its own. A session's calibrated frames are preferred where it has them (photometry on uncalibrated frames carries the bias/dark/flat signature into the magnitudes), falling back to its raw lights where it was never calibrated; soft-deleted frames and rows whose file has since left the disk are skipped; a session with no light frames never appears, since there would be nothing to measure. Object names are matched case- and whitespace-insensitively against the designated name and reported under the designated spelling, so a FITS `OBJECT` of `r leo` doesn't split `R Leo` into a second group. The module holds no Qt, so it is testable against a migrated database alone.

- **`TC-VST-AN-100` tests added** covering the listing (only designated targets, newest session first, empty sessions dropped, case-insensitive narrowing), frame selection (calibrated preferred, raw fallback, missing files and soft-deleted rows skipped) and the empty-library case, against a migrated throwaway library database.

- **`AavsoVspClient` added (`VST-EXT-010`), closing a real gap rather than a stale test.** `TC-VST-EXT-010` had been failing because the AAVSO VSP half of this plugin's external AAVSO interface was never ported: no VSP client existed anywhere, and `VariableStarAnalysis._comparison_stars` was an empty list nothing ever populated, so ensemble differential photometry (`VST-AN-040`) had no comparison stars to work against. `vstarget/planning/vsp_client.py` now fetches a target's comparison-star sequence from the VSP chart API, retrying a stalled request with increasing waits (the API stalls under load) and degrading to an empty chart on failure rather than taking down an analysis run. Stars are returned in the shape `run_photometry` already consumes — `ra`/`dec` converted from VSP's sexagesimal strings to decimal degrees, one `mag_<band>` key per requested filter — with stars lacking a magnitude in the requested band, or carrying unparseable coordinates, dropped. `VariableStarAnalysis.load_comparison_stars()` wires it in. The chart ID travels with the stars since an AAVSO report must cite it, though the report writer still emits a literal `na` in that position.

- **`TC-VST-EXT-010` extended beyond its `hasattr` checks.** The original assertions are kept, and two behavioural tests added: one parses a VSP chart fixture and asserts the dropped-star rules, the per-band ensemble split, and the sexagesimal-to-degrees conversion (cross-checked against `astropy.SkyCoord`); the other asserts a failed lookup yields an empty chart instead of raising.

- **Variable Star Planning panel restored to the standalone VSTarget layout.** `build_vst_page()` previously returned a simplified placeholder (a section text box, a 5-column target table and a 3-field plan form) that bore no resemblance to the application this plugin was ported from. It now returns the real planner: a horizontal split with the AAVSO Variable List on the left — Settings/Download buttons, the nine section checkboxes with Select All/None, the Observable-only / Priority-only / Hide-solar-conj. filters, free-text search, the 10-column sortable target table with priority stars, solar-conjunction greying, rich tooltips and an AAVSO VSX / WebObs / campaign-notice context menu, and Add All Visible / Add Selected — and the Observation Targets plan on the right, with move up/down, Remove, Clear All, the 8-column table whose Filter/Count/Interval/Binning cells edit in place, the running target-and-total-exposure summary, New Target Defaults with Apply to All and Suggest Exposures from Calibration, and a status strip carrying the telescope name, plan-database indicator and working directory. No menu bar is reproduced — Galileo owns the application chrome, and the analysis entries the old File/Analysis/SeeStar menus carried belong to the VS Analysis panel.

- **The plan now creates a Galileo session instead of an iTelescope script (`VST-100`).** Where the standalone app ended at an ACP `.txt` file, the panel's Preview Session / Create Session buttons build one session on Planning > Sessions containing every plan target in RA order: a Target block and one Image block per configured filter (count × interval, binning), with optional Plate solve, Autofocus, Dither and Guiding blocks replacing the old `#defocus`/`#vphot`/`#platesolve`/`#filteroffsets` script directives, which had no meaning in a session. It attaches through the host's own `SessionsPageWidget.create_session_for_target` entry point so the new session inherits the active Pier and that Pier's scheduler, and falls back to writing a `.gses` file when no host window is present. `VST-060`'s ACP exporter is untouched and still serves script-consuming remote-telescope networks.

- **`vstarget/planning/page.py`, `table_models.py` and `session_builder.py` added.** The panel widget, its three Qt item models (`VariableListModel`, `VariableFilterProxy`, `TargetsModel`), and the plan-to-session block builder with its plan validator. Mirrors the standalone app's own split across `main_window.py` + the variable-list/targets mixins.

- **`vstarget/settings.py` and `vstarget/settings_dialog.py` added.** A `QSettings` store under the `Galileo` organisation for the API key, observer code, site, section selection, capture defaults, session block options and working directory, plus the tabbed dialog behind the panel's Settings button. On first use the store seeds itself from the standalone VSTarget application's own settings if present, so an existing user's API key, site and defaults carry over rather than starting blank.

- **`PlanStore` added to `vstarget/planning/database.py`.** SQLite persistence for the Observation Targets table — the plan and its row order survive a restart ("N target(s) restored from previous session"), autosaved on every edit. Lives under Galileo's own data directory via `galileo.platform.get_data_dir()` rather than inventing a path. Separate from the existing `PlanDatabase`, which persists the planner service's `ObservationPlan` objects.

- **`AAVSOTarget`, `ObservingTarget`, `SECTION_CODES`, `SECTION_NAMES` and `TELESCOPE_PRESETS` added to `vstarget/planning/models.py`**, alongside the planner service's existing reduced `AavsoTarget`/`ObservationPlan`. The full Target Tool record is what the variable list sorts, filters and tooltips; `ObservingTarget` pairs one with the per-target capture parameters.

- **`AAVSOClient` and `FetchTargetsThread` added to `vstarget/planning/aavso_client.py`** — the Target Tool v1 `/targets` call (section selection, site-based observability filtering, HTTP Basic auth) and the `QThread` wrapper that keeps a download off the UI thread, with the specific 401/429/410 messages the standalone app gave. The thread class is built lazily so the module still imports without PySide6 present.

- **Exposure-calibration model added to `vstarget/analysis/exposure.py`** — `ExposureCalibration`, `normalize_telescope`, `ExposureSuggestion` and `suggest_exposure`, which the panel's Suggest Exposures from Calibration button needs. Sizes each target's interval for its faint end at the default S/N, hard-capped so comparison stars never saturate, and warns when the bright end could. Measuring a calibration from an image remains an analysis-panel job, so the button reports when none is stored yet.

- **`TC-VST-100` test added** covering RA ordering, one Image block per filter with the right count/exposure/binning, optional blocks staying off unless asked for, and a ragged plan being reported by the validator.

- **`README.md` rewritten to document the CI/CD pipeline.** New sections: repo layout diagram, "How distribution works" flowchart (push → CI → `plugins.json` → Marketplace), updated "Building plugins" covering both CI and local use of `build_plugins.py`, `plugins.json` format reference, and updated "Writing a new plugin" step 6 covering CI-based distribution. Package layout updated to include `ui.py`, `build_zip.py`, and `dist/`.

- **`build_plugins.py` added at the repo root** — generic builder that discovers all plugin directories (any subdirectory containing `plugin.toml`), builds a distribution ZIP for each, and updates the shared `plugins.json` index. Triggered by CI on every push; also usable locally (`python build_plugins.py` or `python build_plugins.py <name>`).

- **`.github/workflows/build-plugin.yml` added** — GitHub Actions workflow that runs `build_plugins.py` on every push to `main` touching `*/plugin.toml` or `*/**/*.py`, then commits the updated ZIPs and `plugins.json` back to the branch.

- **`build_zip.py` converted to a convenience shim.** Delegates to the new repo-level `build_plugins.py`; run `python build_zip.py` from within `vstarget/` as before for local dev. The actual packaging logic now lives in `../build_plugins.py` so it is shared by all plugins in the repo. Run `python build_zip.py` from the repo root to produce `dist/galileo-plugin-vstarget-<version>.zip`, ready to install via Options > Plugins > Install from file or the Marketplace. Reads the version from `plugin.toml`, bundles `plugin.toml` at the archive root plus every `.py` under `vstarget/` (excluding `__pycache__`), and accepts an optional output directory argument.

- **`vstarget/ui.py` — Qt panel pages for both plugin sub-panels.** `build_vst_page()` returns a Variable Star Planning widget with AAVSO target download (by observer section), a filterable target table, and an observation plan builder with ACP script export. `build_vst_analysis_page()` returns a VS Analysis widget with FITS folder selection, photometry parameters, a results table, and AAVSO report export. `VSTPlugin.build_page()` and `VSTAnalysisPlugin.build_page()` in `vstarget/__init__.py` now call these builders instead of returning `None`, so the Science sub-panels show real content rather than a generic placeholder.

- **Initial standalone release.** All code migrated from `galileo/plugins/vstarget/` in the main Galileo repository. Internal imports rewritten from `galileo.plugins.vstarget.*` to `vstarget.*`; `entry_point` in `plugin.toml` set to `"vstarget"` so the package installs correctly as a top-level module via `PluginManager.install()`. Both test suites (`test_vst.py` / `test_vst_an.py`) migrated here with matching import updates. `pyproject.toml` added for `pip install -e ".[test]"` development workflow.
### Fixed

- **AAVSO WebObs Extended-format report emitted 16 fields in the wrong order (`VST-AN-050`).** The format is strictly positional — `NAME,DATE,MAG,MERR,FILT,TRANS,MTYPE,CNAME,CMF,KNAME,KMF,AMASS,GROUP,CHART,NOTES` — and the port had produced `R Leo,...,V,,127,134,,ENSEMBLE,,na,,,,TRANS=NO`: an extra sixteenth field, `TRANS` left blank while the real transform flag was tacked onto the end as `TRANS=NO`, the comparison star sitting in `MTYPE`, the check star in `CNAME`, `ENSEMBLE` in `KNAME`, and blanks where the format requires the literal `na`. Every value from field 6 onward was in the wrong column, so WebObs would have mis-ingested or rejected the submission. The writer now emits exactly fifteen fields in order, with `na` for anything absent, a `#NAME,DATE,…` field-name comment line, and `#OBSCODE` filled from the observer code configured in Settings — WebObs rejects a submission without one, and the header had been shipping an empty `#OBSCODE=`.

- **The VSP chart ID is now actually reported.** `PhotometryResult` gained `chart_id`, `check_mag`, `airmass` and `notes`, and `run_photometry` records the chart its comparison magnitudes came from, so the `CHART` field carries the real ID instead of the hardcoded `na` it previously always wrote. `run_photometry` also now names `ENSEMBLE` as the comparison rather than labelling an ensemble measurement with whichever comparison star happened to be first in the list.

- **`TC-VST-AN-050` strengthened.** The existing assertion (`"#TYPE=EXTENDED" in content or "R Leo" in content`) passed no matter how the fields were arranged, which is why the layout defect survived. A second test now pins the field count and asserts every field's value by name, plus that absent values render as `na` and never as blanks.
